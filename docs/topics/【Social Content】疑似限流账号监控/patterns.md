# 【Social Content】疑似限流账号监控踩坑记录

## dense T+1 状态不能直接代表真实 T+1 观测

- `dws_social_video_state_daily_v2` 会在某天没有真实采集时沿用最近一次累计值，适合日末状态查询，但不等于 T+1 当天一定采到了平台数据
- 实际抽查发现部分 YouTube 发布日期的 T+1 真实快照覆盖率只有约 67%～80%；如果直接使用 dense state，会把采集缺失误判为播放低迷
- 疑似限流中间表应直接以 `dws_social_video_snapshot_daily_v2` 为驱动，只让 T+1 当天存在真实快照的视频进入最近发布次数和周均发布量计算

## Lark 卡片推送：单卡片最多 5 个 table 组件

- 现象：ECN Lark 机器人（`jobs/ads/ads_daily_ecn_lark_push.py`）把三个账号级榜单加成 table 后发送失败，返回 `code=11246 / ErrCode: 11310; card table number over limit`
- 原因：Lark 交互卡片单张卡片最多放 5 个 `table` 组件（配置多语言时每语言各 5 个），原 ECN 卡片已占满 5 张表，再加即超限
- 处理：业务方要求保留 table 展示，因此在**同一个脚本内构建并发送两张卡片**（`send_lark_message` 调两次、同一 webhook），第二张卡片承载三个账号播放波动榜，5 表上限按卡片独立计数；不需要新增脚本
- 备选（不需要 table 时）：把榜单改成 `markdown` 文本渲染，不占 table 配额

## Lark 卡片 markdown 标题：`#` 越少字号越大，`###` 比正文还小

- 现象：模块标题用 `### xxx` 渲染出来比下面 `**加粗**` 正文还小
- 原因：Lark 卡片 markdown 的标题字号规则是「`#` 数量越少字号越大」，`###`（h3）已偏小
- 处理：模块大标题用 `#`（h1）最大号；需要更克制的层级再往下调 `##`/`###`

## 共享准入中间表不要把方向性护栏写进准入条件

- 现象：新增「连续零播放账号榜」时发现，长期零播放账号根本不在 `dws_social_creator_view_fluctuation_daily` 里——它们恰好是最该被抓的对象
- 原因：这张表本意是三张榜共用的**池准入宽表**，但准入 WHERE 里混进了 `baseline_t1_avg_view_count > 0`。这条不是池准入条件，而是「下降榜 / 上升榜要算比例所以基准不能为 0」的方向性护栏，写在共享层就等于替所有下游做了过滤
- 处理：把 `baseline_t1_avg_view_count > 0` 从 DWS 准入下移到下降榜和上升榜各自的 ADS 侧；DWS 只保留真正的池准入（周均发布 > 3、凑满 7 个基准发布日、观察对象 = `D-1`）
- 判断标准：一个条件如果只对**部分**下游成立，就不属于共享准入层。共享层只放「所有下游都必须满足」的条件
- 回归方法：放宽共享层后，用「键集 MD5」比对下游榜单前后是否一字不差，比只比行数可靠——
  `SELECT COUNT(*), TO_HEX(MD5(STRING_AGG(k, ',' ORDER BY k))) FROM (SELECT CONCAT(CAST(dt AS STRING),'|',channel,'|',creator_id) k FROM <table>)`
  注意别用 `SUM(FARM_FINGERPRINT(...))` 做指纹，行数一多就 integer overflow 报错

## 零播放判定必须区分「真实采到 0」和「没采到」

- `dws_social_creator_published_t1_daily` 只收录 T+1 当天存在真实快照的样本，所以该表里的 `observed_t1_view_count = 0` 是**真值 0**，不是采集缺失，可以直接用来判零播放
- 交叉验证方法：看账号在 `dws_social_video_snapshot_daily_v2` 的轨迹。典型死号表现为「视频数持续增长、但播放/点赞总量长期钉在同一个数」——例如某 TikTok 账号 16 天里视频数从 39 涨到 48，播放合计始终是 6506、点赞始终 501，说明老视频历史播放仍在、新视频颗粒不进，是真实限流而非采集异常
- 反例警示：如果换用 `dws_social_video_state_daily_v2`（dense state），沿用值会把缺采伪装成有数据，零播放判定会失真

## 「周均发布 > 3」会把大部分零播放账号挡在池外

- 现象：连续零播放榜命中极少（最近 7 天全平台仅 1 个账号，全量历史 132 天累计 140 个账号日 / 26 个账号），但全站每天有 1~10 个账号 T+1 播放为 0
- 原因：绝大多数零播放账号是低频发布号（14 天 6 条视频，周均约 3），过不了「28 天 > 12 条有效样本」的池门槛；能过门槛的高频号又很少连续 3 个发布日全 0
- 结论：这张榜实际抓的是「高频发布 + 彻底零曝光」的极端情况，常态命中 0~1 个属于口径预期，不是 ETL 故障。看板上这张表经常是空的，别当成数据没跑。若要覆盖低频死号，需为该方向单独放宽发布频率门槛，但那会与另两张榜的同池前提脱钩，属于口径决策而非实现问题

## 布尔判定的需求不要顺手多报一个受窗口截断的计数

- 背景：需求是「最近 3 个发布日的 T+1 播放都是 0」，实现时顺手改成了通用的「连续零播放发布日数」`recent_zero_streak_day_count`，再用 `>= 3` 过滤。两者命中集合完全等价，但多出来的那个计数带来了一个纯负担的歧义
- 问题：连续段只能在最近 8 个发布日的准入窗口内数，取值被截断在 8。`= 8` 的真实语义是「≥ 8，窗口内全为 0」，而看板上就显示一个「8」；`zero_streak_start_dt` 同样只到窗口边界，实际零播放起点可能早得多。抽查的 TikTok 账号窗口内报 8、起点报 8/02，真实是至少连续 14 个发布日为 0、起点在 7/20 之前——按字面读会把「已死一个多月」误判成「刚死半个多月」
- 处理：回到需求本身，只落 `recent_3day_zero_day_count`（0~3）和 `recent_3day_start_dt`，ADS 用 `= 3` 判定；不落任何连续段长度。窗口固定 3 个发布日，两个字段都没有截断语义
- 教训：派生指标的取值范围如果被实现窗口截断，它在看板上就是个会被误读的数字。需求只要布尔判定时，多给一个「看起来更有信息量」的计数是负资产——要么把窗口做到足够大让计数真实可用，要么干脆不报
- 附带收益：去掉 streak 后榜单没有了排序维度，改按 `baseline_t1_avg_view_count` 降序，反而把「历史基准 690 播放、连续 3 个发布日掉到 0」这类真正的从有到无排到了前面，而不是让一堆基准为 0 的长期死号占据榜首
