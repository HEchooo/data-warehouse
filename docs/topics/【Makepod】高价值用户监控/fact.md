# 【Makepod】高价值用户监控

## 报表

- 类型：临时取数，不新增 ADS 表，不修改生产数据；后续如转为固定看板需求，再评估是否下沉 DWS/ADS
- 统计范围：三个自然周
  - `2026-06-28 ~ 2026-07-04`
  - `2026-07-05 ~ 2026-07-11`
  - `2026-07-12 ~ 2026-07-18`（业务方原始需求给的是 `2026-07-02 ~ 2026-07-18`，与前两周重叠且非 7 天，经确认更正为顺延的自然周）
- 粒度：`周 × 支付订单数分桶 × 渠道` 一行
- 产物：`query.sql`

## 字段

以下为业务方原始完整需求字段清单；`每周总支付用户数/订单数/GMV` 三项经用户明确要求，本次结果不产出汇总行，仅保留分桶明细。

| 需求字段 | 落地字段 | 口径 |
|---|---|---|
| 支付1单的用户数、订单数、GMV | `pay_user_count` / `pay_order_count` / `pay_gmv_usd`（`order_bucket = '1单'`） | 周期内按 `user_id` 去重支付成功订单（`pay_status = 4`）计数恰好为 1 的用户 |
| 支付2单的用户数、订单数、GMV | 同上（`order_bucket = '2单'`） | 周期内支付成功订单数恰好为 2 的用户 |
| 支付3单及以上的用户数、订单数、GMV | 同上（`order_bucket = '3单及以上'`） | 周期内支付成功订单数 ≥ 3 的用户 |
| 渠道 | `channel` | 用户维度渠道，来自 `dim_makepod_user_channel.service_user_id`；未命中映射回退 `Organic`，与 `ads_daily_makepod.channel` 口径一致；分桶结果按渠道再拆分 |
| 每周总支付用户数 | 未产出 | 用户明确要求去除汇总行，本次结果不含此字段；如后续需要，可用 `SUM(pay_user_count)` 按周汇总重新计算，或恢复 `query.sql` 中的汇总 `UNION ALL` 分支 |
| 每周总支付订单数 | 未产出 | 同上 |
| 每周支付GMV | 未产出 | 同上 |

补充说明：

- 支付成功口径、GMV 换算方式（`pay_amount + pay_fee` 按 `currency_conversion_dict` 转 USD）、渠道回退规则均对齐 `ads_daily_makepod`／`jobs/dws/dws_makepod_order_daily.py`，避免同一业务口径在不同报表间产生偏差。
- 现有 `ads_daily_makepod` 是 `dt × channel` 每日聚合，直接按周把每天的 `pay_user_count` 相加会导致跨天重复支付的用户被重复计数，因此本次分桶统计直接从 `v3_decom.pay_order` 明细按 `user_id` 在周期内去重后重新聚合，不复用现有日表。
- 同一 `order_id` 只保留最新一条支付记录（`ROW_NUMBER` 去重），避免支付表多次变更导致金额重复放大。
