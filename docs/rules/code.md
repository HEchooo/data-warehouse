# 代码规则

## 分层职责

- `DIM` 负责稳定业务实体、映射关系、归属关系等可复用维度
- `DWS` 负责主题事实沉淀、口径固化，以及可复用分子分母
- `ADS` 负责报表粒度聚合、展示字段和轻派生，不承担跨源复杂建模

默认原则：

- 能被多个主题复用的业务规则，优先沉到 `DIM` / `DWS`
- 不要把“先在 ADS 跑通”当成长期方案
- 如果某条业务规则已经在多个脚本重复出现，应优先抽成稳定中层，而不是继续复制 SQL

## ADS 边界

- `ADS` 层禁止直接读取 `ODS` / `DWD` / 外部服务端源表
- 新增业务口径时，优先先补 `DIM` / `DWS`，再让 `ADS` 消费
- 例外场景必须先和用户确认，并在脚本头部或主题文档中写清：
  - 为什么当前不能下沉
  - 过渡期依赖了哪些源表
  - 后续的收口方向

## 名单与映射

- 团队边界、渠道排除名单、业务归属关系、跨平台统一主键等，不要在多个脚本里各维护一份 Python 常量
- 这类规则优先沉淀到：
  - 维表
  - 稳定中间层
  - `docs/rules/*.md` 中的单一规则文档
- 如果文档和脚本都要表达同一份规则，应保证只有一个代码侧单点来源，其他位置只引用

## DDL

- 如果要修改表中字段，不要修改 `ddl` 目录中现有的 `CREATE TABLE` 语句。
- 应该使用 `ALTER TABLE` 语句在原始定义下方修改字段。

## 更新数据

- 必须使用 `bigquery-safe-table-change skill`

## 路径

- 不要修改代码库中的任何文件路径。
- 这些路径可能直接引用生产环境。

## 清理

- 完成任务后，删除编译生成的文件夹，例如 `__pycache__`。
- 完成任务后，删除回刷脚本等临时文件。

## 可读性

- 每个 CTE 上方要添加中文注释，说明该 CTE 的作用。
- 保持代码高可读性。
- 修改时优先做最小必要变更，不要顺手制造无关重构。
