# 代码规则

## 分层

分层职责、建层判断、层间依赖、每层出口校验，统一以 [layering.md](./layering.md) 为准，本文件不重复。

## 名单与映射

- 团队边界、渠道排除名单、业务归属关系、跨平台统一主键等，不要在多个脚本里各维护一份 Python 常量
- 这类规则优先沉淀到：
  - 维表
  - 稳定中间层
  - `docs/rules/*.md` 中的单一规则文档
- 如果文档和脚本都要表达同一份规则，应保证只有一个代码侧单点来源，其他位置只引用

## 首次口径

- `首日`、`首次`、`第一次发生`、`首次使用`、`首次转化` 这类口径，不要在增量 `DWS` / `ADS` 脚本里直接基于当前处理窗口做 `MIN(dt)` 或 `MIN(gmt_create)` 现算
- 原因：
  - 增量窗口只覆盖最近变更数据时，窗口内最小值不等于全历史首次值
  - 这类口径一旦参与“新增用户”“累计用户”“首日转化”之类指标，窗口截断会直接导致结果失真
- 正确做法：
  - 优先新增单独 `DIM` 表，维护实体级首次发生日期
  - 如果不是严格维表，也至少要沉到稳定中间层，作为代码侧单点来源
  - 后续 `DWS` / `ADS` 只消费这张首次口径表，不再重复全量扫描源表推首日
- 增量维护原则：
  - 首次全量初始化
  - 后续只处理最近变更数据
  - 用 `MERGE` 或等价方式，只向“更早首次值”收敛
- 只有在用户明确接受过渡方案时，才允许临时在下游脚本中直接现算首次口径，并且必须在主题文档中写清后续收口计划

## DDL

- 如果要修改表中字段，不要修改 `ddl` 目录中现有的 `CREATE TABLE` 语句。
- 应该使用 `ALTER TABLE` 语句在原始定义下方修改字段。

## 更新数据

- 必须使用 `bigquery-safe-table-change skill`

## 路径

- 不要修改代码库中的任何文件路径。
- 这些路径可能直接引用生产环境。

## 清理

- 完成任务后，删除编译生成的文件夹，例如 `__pycache__`。
- 完成任务后，删除回刷脚本等临时文件。

## 可读性

- 每个 CTE 上方要添加中文注释，说明该 CTE 的作用。
- 保持代码高可读性。
- 修改时优先做最小必要变更，不要顺手制造无关重构。
