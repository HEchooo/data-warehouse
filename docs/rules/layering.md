# 分层架构规则

本文件是**分层职责、建层判断、层间依赖、每层出口校验**的单一来源。

- 编排顺序、日期判定、窗口回刷见 [pipeline.md](./pipeline.md) 与 [window-incremental.md](./window-incremental.md)
- 脚本写法、DDL 变更、可读性见 [code.md](./code.md)

## 总则

**层数不是目标，每一层必须解决一个具体问题；没有那个问题就不建那层。**

分层规范的意义，是在复杂度真的出现时给它一个安放的地方，不是提前把复杂度制造出来。

每多一层就多了：一次全量落盘（存储与计算成本）、一个调度节点（一个新的故障点）、一段端到端延迟、一处需要同步维护的 schema。加一个字段，三层要改三次，五层要改五次。

## 各层职责

| 层 | 一句话 | 解决的问题 | 绝对不做的事 |
|------|------|------|------|
| `ODS` | 照抄 | 外部数据只能拿一次，不留底就再也回不去 | 不做业务加工，一加工就不是原始的了 |
| `DWD` | 洗干净、拼完整 | 原始数据脏：重复、类型乱、一件事散在多张表 | 不做业务聚合，粒度仍是「一行一件事」 |
| `DIM` | 字典 | 稳定的实体属性与归属关系，多个主题共用 | 不放只有一个主题用的临时映射 |
| `DWS` | 固化口径 | 同一个业务定义在多个报表各写一遍，改一次要改多处 | 不做展示层字段，不承担跨源复杂建模 |
| `ADS` | 给看板吃 | 报表要改列名、加展示字段，不该惊动上游 | 不新建业务口径，不做跨主题建模 |

### 逐层展开

**`ODS`：保真优先。** 唯一职责是把外部数据原样落库，让下游算错时能重算而不必再求外部系统。允许做的只有：格式解析、空值语义统一（例如 API 的 `"-"` 落成 `NULL`）、补采集元信息（`fetched_at`、`report_timezone`、`currency` 这类离开源系统就丢失的上下文）。

**`DWD`：技术性清洗，不是业务性加工。** 去重、类型转换、脏值处理、多源关联打平。判断依据是「这件事换个业务方来做也一样」。

**`DIM`：变化慢 + 被多处引用。** 两个条件都满足才建。团队边界、渠道映射、归属关系、跨平台统一主键、首次发生日期都属于这类。只有一个主题用的映射不要建维表。

**`DWS`：口径的唯一出处。** 核心不是「聚合一下」，而是让业务定义只写一遍。同时负责提供**可复用的分子分母**：可加的计数与金额落库，比率、成本、占比这类不可加的派生值交给下游现算。

**`ADS`：报表粒度聚合与轻派生。** 展示字段、中文标签、单行派生值。改动只影响自己这张表。

## 该不该建某一层

建之前问一句：**把这一层删掉会怎样？**

| 删掉的后果 | 结论 |
|------|------|
| 外部数据丢失，无法重算 | 建 `ODS` |
| 脏数据直接进业务计算，或多源关联要在下游重复写 | 建 `DWD` |
| 同一份映射关系要在多个脚本各维护一份 | 建 `DIM` |
| 同一段业务口径要在多个报表各写一遍 | 建 `DWS` |
| 只是少了一次 `SELECT *` | **不建** |

最后一行是最常见的浪费。一个内容等价于 `SELECT * FROM 上一层` 的层，是纯空转，不要因为「规范里有这一层」就建。

### 允许省略的情况

- **省略 `DWD`**：源数据本身已是聚合好的报表（例如第三方平台的日报 API），没有去重需求、没有多源关联、类型清洗在 `ODS` 落库时已完成
- **省略 `DIM`**：映射关系只有当前一个主题使用
- **省略 `DWS`**：口径不被任何其他主题复用，且不存在可加/不可加指标的混淆风险

省略哪一层，必须在主题 `fact.md` 的 `依赖` 章节写清楚原因，不能默认省略了事。

### 不允许省略的情况

- 接入外部数据源时**必须有 `ODS`**，不允许外部 API 直连 `DWS` / `ADS`
- 口径被两个及以上主题消费时**必须有 `DWS`**，不允许在多个 `ADS` 里各写一份

## 层间依赖

```
外部源 ──▶ ODS ──▶ DWD ──▶ DWS ──▶ ADS ──▶ BI
                    │        ▲
                    └──▶ DIM ┘
```

- `ADS` 只能读 `DWS` / `DIM`，**禁止直接读 `ODS` / `DWD` / 外部服务端源表**
- `DWS` 可以读 `DWD` / `DIM` / `ODS`（源数据已是报表粒度、无 `DWD` 时）
- 禁止反向依赖与同层互相依赖；同层需要复用时，把公共部分下沉一层
- 新增业务口径时，先补 `DIM` / `DWS`，再让 `ADS` 消费；不要把「先在 `ADS` 跑通」当成长期方案
- 同一条业务规则或计算口径在多个脚本重复出现时，应物化到 `DWS` / `DIM` 供下游消费，而不是继续复制 SQL
- 这里的「稳定中层」指数据层（`DWS` / `DIM`），不是共享 Python 模块；`jobs/` 脚本保持自包含，不新增跨脚本共享模块承载口径

### `ADS` 越层的例外

确实无法下沉时，必须先和用户确认，并在脚本头部或主题 `fact.md` 中写清三件事：

1. 为什么当前不能下沉
2. 过渡期依赖了哪些源表
3. 后续的收口方向

例外必须按待收口架构债处理，不当常规模式。

## 每层的出口校验

**每一层写入目标表前都必须自校验，校验不过就失败，不允许静默写入。**

分层最大的风险不是某一层算错，而是**上游断了下游却报告成功**。加列时尤其危险：`ALTER TABLE` 让列在结构上立即存在（值全为 `NULL`），下游 `SELECT` 这一列完全合法、不报错，于是链路断了两层，最下游仍然「刷新完成」。

### 校验分级

不是所有异常都该阻断，全部阻断会让管道天天挂，全部放行等于没有校验。

| 级别 | 判断标准 | 例子 | 处理 |
|------|------|------|------|
| 致命 | 数据错了会导致下游结论错误 | 主键重复、主键为空、分区日期越界、金额没有货币单位、staging 无数据 | 抛错，拒绝写入 |
| 警告 | 影响完整性但不影响核心口径 | 展示字段缺失、少量实体关联不上 | 打 warning 照常写 |

### 强制校验项

每层的 `validate()` 至少覆盖：

- `staging` 行数不为 0
- 主键唯一（`COUNT(*) = COUNT(DISTINCT 主键)`）
- 主键字段无空值
- 本层新增的关键字段无空值

**新增字段时，必须同步给所有经过的层补上该字段的校验**，否则新字段是一个没有守卫的口子，会一路空到看板而没有任何人报错。

### 失败必须原地不动

统一走 `staging 表 → 校验 → 换名` 三步，校验不过就在 staging 阶段失败，目标表一个字节都不被碰过。

禁止对目标表直接 `DELETE + INSERT`：那样校验失败时数据已经被删了一半，才是真正的「下游受影响」。具体做法见 `bigquery-safe-table-change` skill。

### 校验尽量靠上游

同一个约束能在 `ODS` 检查就不要等到 `ADS`。越早拦截，浪费的计算越少、污染面越小。

## 常见反模式

| 反模式 | 问题 |
|------|------|
| 为「符合规范」凑层数 | 空转层带来成本、延迟和故障点，没有任何收益 |
| 把比率、成本、占比直接落在 `DWS` 供下游汇总 | 率值不可加，下游 `SUM` 或 `AVG` 必然算错；只落可加的分子分母 |
| 在增量脚本里现算「首次 / 首日」 | 窗口只覆盖最近数据，窗口内最小值不等于全历史首次值，详见 [code.md](./code.md) |
| `ADS` 直接读 `ODS` 图省事 | 口径散落在展示层，换一个报表就要重写一遍 |
| 新增字段只改最下游 | 上游没值，下游静默写 `NULL`，链路断了却报告成功 |
| 同一份名单在多个脚本各维护一份常量 | 改一处漏一处，应沉淀到维表或规则文档 |
