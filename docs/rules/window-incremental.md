# 维表窗口增量更新规则

## 目标

给 `DIM / DWS / ADS` 中适合“窗口增量”模式的任务提供统一规则。

这里的“窗口增量”指：

- 同一份脚本同时兼容初始化和增量
- 目标表不存在或为空时，自动全量初始化
- 目标表已存在时，固定回看最近一段时间的源表变更窗口
- 按业务主键做 upsert，而不是整表全量重刷

先明确一个边界：

- “窗口增量”只定义**单个表级脚本**如何更新自己的目标表
- 它不等于“多张表共享一套待处理 `dt` 发现逻辑”
- 不要为了复用入口，把多个上游不同、补数边界不同的任务硬塞进同一个共享日期脚本


## 默认窗口

- 远端 cron 当前频率为每小时 2 次
- 默认窗口统一使用最近 `6` 小时
- 除非用户明确要求，不要各脚本自行发散成不同窗口

默认写法：

```sql
WHERE source_update_ts >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 6 HOUR)
```


## 适用条件

只有满足下面条件时，才优先使用窗口增量：

- 源表存在稳定的更新时间字段，例如 `gmt_update`
- 目标表有明确业务主键，可以安全做 upsert
- 任务允许用固定窗口覆盖短期调度抖动
- 窗口内重复重算不会导致错误累计

典型适用场景：

- 维表同步：`DIM`
- 可按主键替换的轻量 `DWS`
- 本质上只是汇总上游最近变更键的 `ADS`


## 不适用条件

下面场景不要直接套用窗口增量：

- 源表只有 `create_time`，没有可靠 `gmt_update`
- 历史记录会被频繁修改，但窗口外修改不能接受漏数
- 调度中断可能长期超过 `6` 小时
- 指标是分区级全量重算语义，而不是主键 upsert 语义
- 存在流式写入风险，不能安全使用直接 `DELETE / INSERT`
- 单表同时依赖多类上游，而且这些上游没有同一套可靠水位，例如同时依赖事件表、服务端事实表、维表修正

这类场景不要退化成“共享一组 `dt` 给所有脚本一起跑”。

这类场景要么改成全量重建，要么改成更强的水位 / state 管理方案，再和用户确认。


## 时间字段选择

- 窗口增量优先使用 `gmt_update`
- 不要默认按 `create_time` 做增量

原因：

- `create_time` 只能抓新增，抓不到历史记录更新
- 维表字段如 `status`、`title`、`nickname` 这类都可能更新
- 只按 `create_time` 会导致老记录变更漏同步

如果源表只有 `create_time`，先明确告诉用户风险，再决定是否接受“只保新增”的方案。


## 脚本模式

窗口增量脚本默认遵守以下模式：

1. 先判断目标表是否存在，或是否为空
2. 不存在 / 空表时走全量初始化
3. 已存在时只读取最近 `6` 小时 `gmt_update` 窗口
4. 把窗口内源数据先按业务主键去重
5. 再和目标表做 key-based upsert
6. 最终保留目标表自己的 `update_time`

不要求脚本通过外部参数区分“初始化”或“增量”。

补充要求：

- 表级脚本自己负责判断本表待处理范围，或由任务级编排显式传入本表 `dates`
- 不要新增跨主题、跨多表复用的公共“日期发现层”
- 如果某张表是分区重算语义，脚本可以只负责“对传入 `dates` 做幂等重算”，但“哪些 `dates` 要刷”仍然必须按该表自己的上游来决定


## 分区重算型任务

有些任务本质上不是“窗口增量 upsert”，而是“指定日期分区重算”。

典型特征：

- 目标表天然按 `dt` 分区重建
- 同一天结果依赖多张上游表的并集
- 同一个业务主键不适合单行 upsert
- 使用 `DELETE dt + INSERT dt` 比 key-based upsert 更稳

这类任务的正确边界是：

- 脚本内部只负责对给定 `dates` 做幂等重算
- `dates` 必须由该任务自己的上游水位、补数策略或外部任务编排单独决定
- 不能因为几个任务都叫 `DWS`，就共享同一组待处理 `dt`
- 如果多源上游没有统一可靠水位，可以固定重刷最近 N 天分区，但必须显式写清窗口大小和历史回填边界


## 字段语义

- 目标表里的 `update_time` 只表示这张表本次被 ETL 写入的时间
- 不要把 `update_time` 混用成源表变更水位
- 如果只是窗口增量方案，默认不强制把源侧更新时间字段落进目标表


## Upsert 要求

- 必须先在窗口内按主键去重，再写目标表
- 必须避免同一主键在最终结果里出现多行
- BigQuery 更新仍遵循安全变更思路，优先 staging + changed table + swap

典型写法：

```sql
SELECT *
FROM target
WHERE business_key NOT IN (
  SELECT business_key FROM staging
)
UNION ALL
SELECT *
FROM staging
```


## 风险边界

窗口增量不是强一致方案，必须明确它的边界：

- 如果远端停跑超过 `6` 小时，窗口外的变更可能漏掉
- 如果源表存在超过 `6` 小时的晚到更新，窗口外的变更可能漏掉
- 如果后续业务要求“绝不能漏历史更新”，应升级为更强水位方案，而不是继续扩大窗口

对分区重算型任务，还要额外注意：

- 如果 `dates` 的发现逻辑只看某一张上游表，其他上游的晚到或修正会漏刷
- 如果维表修正会影响历史映射，必须单独评估是否回刷历史分区
- 共享日期入口会把“单表上游边界”错误放大成“整层共享边界”

因此：

- 默认先用 `6` 小时窗口换性能
- 一旦业务要求超出窗口保障范围，先和用户确认再升级方案
